# 场景实现指南

## 1. 场景与系统能力映射

### 1.1 场景总览

| 编号 | 场景 | 阶段 | 优先级 | 涉及 Agent | 涉及工作流 |
|------|------|------|--------|-----------|-----------|
| S1 | 新需求生成 | Phase 1 | P0 | 需求理解、澄清、拆解、PRD生成、流程设计、评审、同步 | NewRequirementWorkflow |
| S2 | 原型驱动需求 | Phase 2 | P1 | 原型解析、PRD生成、同步 | PrototypeDrivenWorkflow |
| S3 | HTML/系统反推需求 | Phase 3 | P2 | 原型解析、PRD生成、同步 | PrototypeDrivenWorkflow |
| S4 | 流程图驱动需求 | Phase 3 | P2 | 流程设计、PRD生成、同步 | FlowDrivenWorkflow |
| S5 | 存量系统升级需求 | Phase 4 | P2 | 存量系统分析、PRD生成、评审 | LegacyUpgradeWorkflow |
| S6 | 需求迭代 | Phase 2 | P1 | 需求理解、拆解、PRD生成、同步 | RequirementIterationWorkflow |
| S7 | 局部修改 | Phase 1 | P0 | 同步 Agent + 对应领域 Agent | CommandExecutionWorkflow |
| S8 | 需求评审与优化 | Phase 1 | P0 | 需求评审 | ReviewWorkflow |

### 1.2 场景设计原则

每个场景必须满足：

```
✅ 实时可见     → SSE 流式推送执行过程
✅ 实时可控     → 指令队列支持随时干预
✅ 可提问       → 异步反馈机制
✅ 可迭代       → 局部修正不影响全局
✅ 数据统一     → 所有产出落到 DSL
```

## 3. S7：局部修改（指令队列核心场景）

### 3.1 支持的修改类型

| 类型 | 示例 | 影响范围 |
|------|------|---------|
| `modify` | "把订单列表的状态字段改为下拉选择" | pages → PRD |
| `add` | "增加一个导出功能" | features → pages → PRD |
| `delete` | "删除审批流程" | flows → features → PRD |
| `recompute` | "重新生成数据模型" | entities → pages |
| `clarify` | "解释一下审批流程的设计" | 不修改数据，只回复 |

### 3.2 修改触发方式

```
方式1: 对话区直接输入
  用户: "把订单列表增加一列创建时间"
  → 系统识别为 modify 指令
  → 自动定位 target: pages.order_list.table.columns

方式2: 选中内容修改
  用户选中 PRD 中 "单级审批" 文字
  → 点击 "AI 修改"
  → 输入 "改为三级审批"
  → 系统定位 target: flows.order_approve

方式3: 右键菜单
  用户右键结构树的 "订单管理" 节点
  → 选择 "AI 优化"
  → 系统生成 recompute 指令

方式4: 流程图操作
  用户在流程图中删除 "部门审批" 节点
  → 系统生成 delete 指令
  → target: flows.order_approve.nodes.dept_approve
```

### 3.3 局部更新机制

```
指令: "在订单列表增加一列创建人"

执行过程:
1. 解析指令 → type: add, target: pages[order_list].table.columns
2. 加载 DSL，定位到目标节点
3. Agent 生成修改:
   columns: [
     ...existing,
+    { field: "creator", label: "创建人" }
   ]
4. 更新 DSL (仅修改目标节点)
5. 同步 Agent 计算影响:
   - entities.order 需要增加 creator 字段
   - PRD 相关章节需要更新
6. 执行同步更新
7. SSE 推送增量更新到前端
8. 前端局部刷新（非全量重渲染）
```

## 4. S2：原型驱动需求

### 4.1 流程

```
用户上传原型 (HTML/截图/Figma导出)
         │
         ▼
  ┌──────────────┐
  │ 原型解析 Agent │
  │              │
  │ HTML → DOM解析│
  │ 图片 → UI识别 │
  └──────┬───────┘
         │
         ▼
  生成 DSL pages 结构
  {
    pages: [{
      name: "从原型识别的页面名",
      components: [
        { type: "table", columns: [...] },
        { type: "form", fields: [...] }
      ]
    }]
  }
         │
         ▼
  用户确认/修改页面结构
         │
         ▼
  PRD 生成 Agent → 基于页面结构生成需求文档
         │
         ▼
  DSL 同步 → 完善 features / entities / rules
```

         │
         ▼

           │
           ▼

  {
    tech_stack: { language: "Java", framework: "Spring Boot" },

    data_model: { tables: [...], relations: [...] },

           ▼

           │

## 6. S8：需求评审与优化

### 6.1 评审维度

```
评审维度:
├── 完整性 (25%)
│   ├── 功能点是否都有页面设计
│   ├── 页面是否都有字段定义
│   ├── 流程是否覆盖异常场景
│   ├── 实体是否有完整字段
│   └── 非功能需求是否完整
├── 一致性 (25%)
│   ├── PRD 描述与 DSL 是否一致
│   ├── 流程与功能是否对应
│   ├── 页面字段与实体字段是否匹配
│   └── 权限定义是否一致
├── 可行性 (25%)
│   ├── 技术可行性
│   ├── 资源可行性
│   └── 时间可行性
└── 规范性 (25%)
    ├── 命名规范
    ├── 字段类型合理性
    ├── 权限粒度合理性
    └── 文档格式规范
```
